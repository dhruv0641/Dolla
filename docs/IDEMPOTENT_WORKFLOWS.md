# Idempotent workflow dispatch

`OutboxDispatcher` accepts only rows already leased by `lease_due_jobs`. Convert each returned eight-column row with `LeasedJob.from_row`, then dispatch using the worker ID that acquired the lease. The row includes the configured maximum attempt count. The dispatcher requires an exact lease-owner match; an unregistered event is marked non-retryable and dead-lettered.

For a registered job, the handler runs inside `unit_of_work`, and `complete_job` acknowledges the same job in that same transaction only while the lease owner, attempt count (lease generation), and unexpired lease match. If the handler raises or completion detects lease loss/expiry, the transaction rolls back, including handler database writes. A job's immutable UUID is its stable idempotency key. Handlers must make their database/outbox writes unique or upsert-safe by that key and must not call external services, perform network I/O, or produce non-transactional side effects. This keeps a redelivery from duplicating committed work.

This is an at-least-once lease mechanism with transactional database effects; it does not provide exactly-once delivery to external systems. Handler failures use safe error codes and bounded exponential retry delays; exhausted jobs move to `DEAD`. See [OUTBOX_RETRIES.md](OUTBOX_RETRIES.md) for operator visibility and replay rules. No live worker or PostgreSQL instance is configured, so current evidence is unit tests with fake connection/pool boundaries only.
