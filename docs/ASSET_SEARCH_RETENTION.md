# Asset search and retention

`AssetCatalogRepository.search` returns active assets for an authenticated owner. Filters can narrow by brand, content, scene, kind and MIME. Results use a bounded limit (1–100) and a stable `(created_at, asset_id)` keyset cursor. Owner scope and active state are enforced in SQL. The repository returns metadata; it does not expose local storage paths or issue signed downloads.

Retention is an explicit operator action. `tombstone` requires an owner ID, asset UUID, reason and an aware cutoff timestamp in the past. It accepts only an old asset whose content is `ARCHIVED` and has no approved-scene, QA, review, render or publication references. It retains the full metadata and payload, records the actor/reason/time, and removes the asset from normal search/listing. Repeating it is idempotent. There is no age-based scheduler or default deletion date.

`AssetPurgeService.purge` is a separate, deliberate cleanup operation. Its repository first rechecks ownership, archived content and references under row locks, then commits `PURGE_PENDING`. The local worker derives the object path from the asset UUID under the managed root, rejects symlinks, nonregular files and extra hard links, verifies SHA-256 and size, then writes/fsyncs a temporary same-directory intent file and atomically links it into place before unlink. On POSIX, it fsyncs the object directory both after publishing the marker and after unlink. Only after unlink succeeds does it record `PURGED`; a retry with the matching marker can finish a prior unlink whose DB write failed. The marker remains as a permanent UUID reservation, so the storage writer refuses to recreate purged bytes. Metadata and lineage remain in PostgreSQL. A failed unlink or changed hash leaves `PURGE_PENDING`; investigate it before retrying. A missing file without a matching marker also stays pending for reconciliation. An already `PURGED` asset returns without another deletion. On Windows, directory-entry crash durability is not verified by this implementation; operators must reconcile the filesystem with database state after a crash before making a durability claim.

Migration `0010` makes retention states durable and adds reference-writer triggers. Direct references from scenes, QA, reviews, render outputs and publications must point to an `ACTIVE` asset. Each writer locks the asset row, serializing with retirement. Render input manifests must be an exact object `{ "asset_ids": ["canonical-uuid", ...] }` containing 1–100 active assets of the same content. The render trigger locks the content and asset rows; retirement also locks them. Other render command settings belong in `command_manifest`. The migration **fails closed if any legacy render jobs already exist**, because their free-form manifest references cannot be proved safe automatically. Operators must audit/migrate those rows before applying this migration. Archived content with retired assets cannot be reactivated. Purge also conservatively requires no render jobs for the candidate content.

Operators should back up media and inspect all consumers before invoking purge. Application DB and filesystem operations cannot be one atomic transaction. `PURGE_PENDING` plus the intent marker are recovery evidence for crashes or DB failure after unlink. The local deletion method assumes other processes cannot mutate the managed storage root concurrently; its path/integrity checks are a guard, not a filesystem access-control replacement. There is no live PostgreSQL trigger or lock test in this task, and no production cleanup was performed.
