# Flow MCP adapter boundary

`CapabilityGatedFlowAdapter` is the app-side safety boundary for a future Flow MCP transport. It is deliberately not wired to the Codex desktop tool catalog: the host exposes Flow MCP tools to this session, but the repository has no verified transport endpoint or deployment identity. A `ManifestProvider` and `McpTransport` must be supplied by a separately authorized runtime integration.

The adapter is disabled by default. When enabled, it requires an expected server ID and opaque local account reference, a verified account authorization, a fresh manifest (15 minutes by default), an explicit normalized-operation binding to a tool present in that manifest, and arguments satisfying the supported discovered JSON Schema subset. Schemas are copied and recursively frozen; unsupported keywords, malformed constraints, or invalid argument values fail closed. Video generation or any other spending binding additionally requires an approval reference scoped to the same account and operation with a positive maximum credit ceiling, plus an injected trusted `SpendAuthorizationVerifier`. No email, cookies, access tokens, or credentials belong in these objects.

`FlowAccountHealthSnapshot` separates MCP connectivity, Flow login, explicit identity verification, opaque account reference, and check time. `FlowAccountHealthService` reads and type-checks evidence from an injected provider, then classifies stale, disconnected, logged-out, unknown-identity, mismatched-account and ready states. Only that service can issue a short-lived `FlowAccountAuthorization`; the adapter rechecks its validity window immediately before transport invocation, after awaited capability and approval checks. A successful connector login alone never proves the configured Google identity. The user approved the identity shown directly in Flow, but this application still has no provider configured to map verified external identity into a local opaque account reference; no application account authorization is currently issued.

Failures use stable `FlowAdapterError` codes and sanitized messages. Raw MCP exceptions and remote result data are untrusted. The adapter only verifies that a result is a mapping; callers must validate operation-specific fields, file paths, media bytes, job state, idempotency, and credit reconciliation before using them. `JOB_RESUME` is a distinct, non-spend operation and rejects any call unless `job_id` is present, `resume` is exactly true, `auto_confirm` is exactly false, and arguments are limited to the existing job ID plus Flow's required resume context (`project_url`, original `prompt`, and `output_dir`). The context must come from the persisted original job, never a new caller prompt. It still requires an explicit manifest binding to an inspected tool schema. The trusted verifier proves that the human approval reference and ceiling are valid; until a verified quote or conservative cost table exists, this boundary cannot prove actual spend stays below that ceiling and must not be used to authorize unattended paid generation.

No app-side live transport is configured and no generation was submitted; production integration is not claimed. The Codex Flow session is a separate runtime surface and is not wired into the application transport. Current observed capabilities and external prerequisites are tracked in `MCP_CAPABILITY_MATRIX.md`; the old-job outcome remains unknown under TASK-024.
